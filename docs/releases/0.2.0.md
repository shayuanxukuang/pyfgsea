# PyFgsea 0.2.0 release note

Status: unreleased. The clean `0.2.0rc3` candidate is being rebuilt from the
official PyFgsea history. No candidate described here is a final release or an
accepted manuscript artifact.

```text
SOURCE_REPAIR_MIGRATED_TO_OFFICIAL_HISTORY
ARTIFACT_AND_MANUSCRIPT_CLOSURE_PENDING
```

## Repository-history boundary

The earlier `v0.2.0-rc1` and `v0.2.0-rc2` candidates were created on the TED
companion repository history, which has no common ancestor with the official
PyFgsea `main`. They are superseded repository-integration candidates. They
must not be merged into PyFgsea `main`, used as the ancestry of a final
release, or have their existing tags moved.

The replacement release branch starts at official PyFgsea commit
`2b047dc557604018b28d82fa3da9ab496e1955a4`. Only the Rust GSEA repair, its
Python wrapper, narrowly related trajectory parameters, pure PyFgsea tests,
and release/reproducibility definitions are migrated. TED, BIB, T21 and other
companion-project code and metadata are outside this release.

## Candidate versioning

The release-candidate distribution version is `0.2.0rc3`; its prospective Git
tag is `v0.2.0-rc3`. The final version will become `0.2.0` only after the
source, sdist-to-wheel, installed-wheel, cross-platform, reference-environment,
and manuscript-impact gates pass. Candidate files must not be uploaded under
the final `0.2.0` distribution version.

The legacy `.github/workflows/release.yml` is therefore a manual build preview
and contains no publication job. Final PyPI/GitHub publication must consume the
same files and receipts that passed the artifact-chain workflow; it must not
rebuild unrelated wheels in a parallel tag-triggered workflow.

## Statistical compatibility boundary

PyFgsea 0.2.0 targets an explicitly named current-reference lane based on R
fgsea 1.38.0 and keeps the publication-reference lane based on fgsea 1.32.2
separate. Results from the two lanes must not be pooled or described as one
unnamed “fgsea reference.” The machine-readable definitions are in
`reference_manifest.json`.

The source repair includes score-type handling, deterministic tie handling,
exact pathway-size nulls in aligned mode, explicit unresolved/failure states,
and the fgsea 1.38 / upstream issue-151 regression cases. These statements are
implementation scope, not evidence that the final cross-platform artifacts or
manuscript figures have passed.

The low-level `build_tail_curve` and `query_tail_curve` names remain available
for compatibility but are deprecated. They expose an approximate legacy
empirical helper, not the aligned multilevel estimator. Its returned
`TailCurve` records the canonical score type and sign, `approximate=True`, and
the `legacy-empirical-tail-v1` algorithm revision; incompatible queries are
rejected instead of silently reinterpreting the stored null population.

The never-implemented `run_scanpy` name is no longer advertised through the
top-level `__all__`; earlier releases listed it even though no callable existed.
The public trajectory plotting functions now delegate to their maintained
implementations instead of returning silently from placeholder stubs. Core
runtime dependencies are separated from the `trajectory` extra, and unused
TED/full-stack dependencies are not part of the PyFgsea distribution.
Calling `plot_pathway_dynamics` without a pathway list now raises a clear
`ValueError` instead of silently returning from the old no-op placeholder.

### Migration from 0.1.4 defaults

The 0.2.0 defaults are intentionally not numerically interchangeable with
0.1.4. Users must record the selected mode and parameters when comparing old
and new results.

| Setting | 0.1.4 default | 0.2.0rc3 default |
| --- | --- | --- |
| high-level score type | `two_sided_abs` | `std` |
| estimator contract | implicit legacy behavior | `mode="aligned"` |
| high-level pathway-size binning | `None` | `0` (exact size) |
| trajectory `step` | `100` | `50` |
| trajectory `nperm_nes` | `100` | `2000` |
| trajectory `bin_width` | `10` | `0` (exact size) |
| trajectory NES cache | on | off |
| trajectory window RNG | `seed + window_id` | stable master seed with ranking-bound streams |

The deprecated `score_type="two_sided_abs"` remains available for a bounded
legacy-like absolute-tail calculation, but it is marked approximate and is not
equivalent to current R `fgseaMultilevel(scoreType="std")`. There is no promise
that one 0.2.0 option set reproduces 0.1.4 byte-for-byte; publication-history
audits must run the frozen 0.1.4 / fgsea 1.32.2 lane instead. New work should
select `mode="aligned"`, `score_type="std"`, `bin_width=0`, and an explicit
tie policy.

## Figure 2 parameter contract

The author accepted the following formal GSE155254 Figure 2 calculation
contract on 2026-09-01:

- `window_size=500`
- `step=50`
- `nperm_nes=2000`
- `score_type="std"`
- exact pathway sizes (`mode="aligned"`, `bin_width=0`)
- NES cache disabled

The versioned record is
`repro/figure2_gse155254/author_parameter_contract.json`. Parameter acceptance
does not accept a recalculated figure or a manuscript conclusion. A formal
receipt still requires a clean annotated release-candidate commit, a verified
installed wheel/native core, frozen input hashes, and output hashes.

## Remaining release gates

RC3 uses a two-stage tag gate. First, the clean candidate commit must pass the
local source and sdist-to-wheel checks. An annotated `v0.2.0-rc3` candidate tag
is then created locally and pushed to trigger the immutable cross-platform and
reference-OCI workflow. The candidate is not published or promoted unless that
workflow passes. The remaining gates are:

1. source tests and Rust tests from the clean branch;
2. local sdist creation, wheel construction from that sdist, clean-environment
   installation, version/core checks, and installed-wheel regression tests;
3. Linux, Windows and macOS artifact-chain receipts;
4. built OCI digests and embedded receipts for both R reference profiles;
5. the legacy/current Figure 1 dual-lane run;
6. formal Figure 2 recalculation and binding;
7. supplementary-result and manuscript-impact audits.

Until those gates pass, the correct project state is:

```text
SOURCE_LEVEL_REPAIR_IN_VALIDATION
ARTIFACT_AND_MANUSCRIPT_CLOSURE_PENDING
```

GitHub Actions artifacts are temporary transport, not permanent research
archives. Before their retention window expires, the exact platform bundles,
OCI receipts, and SHA-256 manifests that pass the gate must be attached to the
GitHub Release and preserved in the corresponding Zenodo version.
